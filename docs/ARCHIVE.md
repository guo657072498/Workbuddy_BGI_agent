# 归档执行手册

用户说**「归档」**时，按本手册的 6 步顺序执行。**不得跳步，不得因为"看起来没问题"就省略检查。**

---

## 第 1 步 · 范围确认

```bash
git status --porcelain -uall
```

- 列清本次改动涉及的**任务**和**文件数**
- **先向用户复述**："本次将归档 `tasks/xxx`，涉及 N 个文件，其中 M 个是二进制产物"
- 若发现**不属于该任务**的改动（比如顺手改的配置、别的任务的草稿），单独问是否一起提交
- 若有未跟踪的新任务文件夹，确认它是否属于本次归档范围

---

## 第 2 步 · 敏感信息扫描（强制，无例外）

按下面四项逐一检查，**任一命中即停止归档**，先处理再重启流程。

### 2.1 凭据文件

```bash
git add -A --dry-run | grep -iE "\.env|\.pem|\.key|credential|secret|token|password"
```

命中 → 检查是否会入库；若已入库则移除并加进 `.gitignore`。

### 2.2 代码里的硬编码密钥

```bash
git diff --cached -U0 | grep -inE "password|passwd|secret|token|api[_-]?key|access[_-]?key" | head -30
```

排除变量名、注释后确认为真实密钥 → 停止，改为读环境变量或配置文件。

### 2.3 样例数据里的真实信息（**办公类任务最高风险项**）

这是最容易出事的地方。检查 `samples/`、`deliverables/`、测试数据里是否含：

- 真实客户名称、联系人、电话、身份证号、地址
- 真实病历、诊断信息、患者姓名（本仓库做过 UDI 医疗器械相关任务，尤其注意）
- 真实员工姓名、工号、薪酬

含真实信息 → 替换为脱敏样例（姓名改"张三"、编号改规律数字），**不是删掉了事**，因为样例本身有价值。

### 2.4 Office 文档属性

交付出去的 Excel/Word/PDF，其"文档属性"里可能带作者名、公司名、原始路径。
对**要给外部**的成品，检查一下；内部留档可放宽。

---

## 第 3 步 · 体积与产物检查

### 3.1 体积阈值

```bash
git add -A --dry-run | sed 's/^add //' | tr -d "'" | while read -r f; do
  [ -f "$f" ] && echo "$(stat -c%s "$f") $f"
done | sort -rn | head -10
```

| 单文件体积 | 处理 |
|---|---|
| > 50 MB | **禁止入库**。改放外部存储，README 里记来源 |
| 10~50 MB | 允许入库，但 commit message 必须注明体积 |
| < 10 MB | 正常入库 |

> 参照：GitHub 单文件硬上限 100 MB，超过会拒绝推送。

### 3.2 产物误入检查

```bash
git add -A --dry-run | grep -E "_out/|/output/|输出结果/"
```

**有任何输出 → 立即停止。** 这说明 `.gitignore` 失效，或文件被放错了位置（成品应按规范放 `dist/` 或 `deliverables/`）。

### 3.3 构建中间产物

```bash
git add -A --dry-run | grep -E "build/|__pycache__|\.pyc$|\.egg-info"
```

有输出 → 停止，检查 `.gitignore`。

---

## 第 4 步 · 规范一致性检查

逐项打勾：

- [ ] 任务目录名符合 `YYYYMMDD-<英文短名>`（日期是创建日，未被改动过）
- [ ] 任务根有 `README.md`
- [ ] 该 README 里写明了**交付物在哪**（`dist/` 或 `deliverables/` 的具体路径）
- [ ] 根 `README.md` 索引表里有该任务行，且状态列用词在词表内
- [ ] 根索引的「位置」链接能点到（路径正确、含日期前缀）
- [ ] 若本任务产生了新交付物，其路径已写进任务 README

---

## 第 5 步 · 更新索引与日志

### 5.1 根 README 索引

- 新任务：加一行
- 已有任务：更新状态列（如 `进行中` → `已完成`）
- 核对：`tasks/` 下每个目录（除 `_template`）都必须有对应行

### 5.2 工作日志

在 `.workbuddy/memory/YYYY-MM-DD.md` 追加 3~5 行：

```
## 归档 <任务名>

- 做了什么（一句话）
- 关键决策 / 踩过的坑（如有）
- 遗留问题 / 下一步（如有）
```

日志是 append-only，**不要覆盖已有内容**。文件不存在则新建。

---

## 第 6 步 · 提交与推送

```bash
git add -A
git commit -m "<类型>(<任务名>): <说明>"
git push origin main
```

### 提交信息格式

`<类型>(<任务名>): <中文说明>`

| 类型 | 场景 | 示例 |
|---|---|---|
| `feat` | 新任务 / 新功能 | `feat(20261026-udi-xml-tool): 支持 zip 批量转换` |
| `fix` | 修 bug | `fix(20261026-udi-xml-tool): 修正箱码切块逻辑` |
| `docs` | 只改文档 | `docs: 更新任务索引` |
| `chore` | 规范、配置 | `chore: 修正 gitignore 的 dist 规则` |
| `archive` | 归档动作 | `archive(20261026-udi-xml-tool): 完成归档` |

### 推送后

- 报告推送到哪个分支、commit hash、涉及文件数
- 若推送失败（网络/权限），如实报告，不要假装成功

## 入库判据速查

| 对象 | 结论 | 理由 |
|---|---|---|
| `dist/` 里的最终 exe / 安装包 | **入库** | 用户双击用的成品，不入库则仓库对该任务零价值 |
| `deliverables/` 里的成品 Excel/Word/PDF | **入库** | 结论态文档 |
| 源码、配置、bat、spec | **入库** | 文本，体积小 |
| `_out/`、`output/`、`输出结果/` | **不入库** | 可由代码或输入重新生成 |
| 依赖（`node_modules`、`.venv`、`__pycache__`） | **不入库** | 可重装 |
| > 50MB 原始数据 | **不入库** | README 记来源 |
| 含密钥或真实个人信息的文件 | **不入库** | 安全底线；样例需脱敏 |

### exe 更新策略

**只在版本发布时重新打包入库**，日常改代码不重复提交 exe。
理由：每次打包都会产生全新的二进制 blob，git 无法增量存储，仓库会快速膨胀。

## 常见问题

**Q：归档后发现漏了文件，怎么办？**
补一次 commit 即可，不必 `--amend`。历史多一条提交是可接受的，改写历史反而危险。

**Q：任务做到一半，用户说"归档"？**
照常执行，但状态列填 `进行中` 或 `暂停`。归档不等于任务完成，它只是"把当前进度安全存到远端"。

**Q：用户说"彻底归档"或"这里不用了"？**
这种情况下才考虑把任务移入 `archive/` 目录。移动用 `git mv`，并在根索引的状态列改为 `已归档`。
默认的「归档」**不移动文件夹**。

**Q：`git push` 要求输入密码？**
说明凭据没配好。报告给用户，不要尝试在对话里索取密码。
