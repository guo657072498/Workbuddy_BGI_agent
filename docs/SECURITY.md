# 敏感信息规范

本文件是**敏感信息规则的唯一权威清单**。README、`docs/ARCHIVE.md`、`.gitignore` 三处如与本文件冲突，以本文件为准。

仓库为私有，但私有 ≠ 安全。以下是硬底线，**任何一条命中都不得入库**。

---

## 1. 凭据与密钥（文件级）

严禁入库：

| 类型 | 示例 |
|---|---|
| 环境变量文件 | `.env`、`.env.local`、`.env.production` |
| 证书 / 私钥 | `*.pem`、`*.key`、`*.pfx`、`*.p12` |
| 凭据 JSON | `secrets.json`、`credentials.json`、`token.json`、`*_credentials.*` |
| 平台访问令牌 | 任何第三方平台的 API Key、Access Token、Webhook 地址 |
| 浏览器 / 会话导出 | cookie 导出文件、登录态快照 |

`.gitignore` 已覆盖上表（第 45-54 行），但 **`.gitignore` 只防"未跟踪的新文件"，防不住已经被跟踪过的文件**。历史上入库过的凭据必须主动移除。

---

## 2. 代码里的硬编码密钥（内容级）

`.gitignore` 管不到这里——密钥写在 `.py` 里照样会被提交。

**判定口径**：出现 `password` / `secret` / `token` / `api_key` / `access_key` 等字样时，逐一确认：

- 是**变量名、参数名、注释、占位符**（`YOUR_API_KEY`、`os.getenv(...)`）→ 安全
- 是**可用的字符串字面量** → 违规，改为读环境变量或本地配置文件

---

## 3. 真实个人信息（**办公类任务最高风险项**）

这是本项目最容易出事的地方：办公自动化的输入几乎都是真实业务数据。

| 数据类型 | 具体字段 |
|---|---|
| 客户 / 供应商 | 真实单位名称、联系人、手机号、地址、合同编号 |
| 患者 / 医疗器械 | 患者姓名、病历号、诊断信息、手术记录；UDI 相关的真实生产批次与流通信息 |
| 员工 | 姓名、工号、身份证号、薪酬、考勤、绩效 |
| 其他 | 银行卡号、社保号、车牌号、人脸照片 |

### 处理原则

**不是"删掉就完事"，而是替换为脱敏样例。**

`samples/` 里的样例本身有长期价值（用来回归测试解析逻辑），直接删除会让任务失去可复现性。正确做法：

| 字段 | 替换为 |
|---|---|
| 姓名 | 张三 / 李四 / 王五 |
| 手机号 | 13800000001、13800000002…（规律递增） |
| 身份证号 | 保留位数与校验位格式，中间位改 0 |
| 单位名称 | XX 医疗器械有限公司 |
| UDI 码（30 位） | 保留 30 位纯数字，末 4 位按序递增，前缀统一 |
| 日期 | 统一后移到某一基准年，保持相对间隔不变 |

**脱敏后必须再跑一次程序**，确认逻辑仍然通过——脱敏改变了码的规律性，可能暴露原本隐藏的解析 bug。

---

## 4. Office 文档属性

Excel / Word / PDF 的"文档属性"常带作者名、公司名、原始磁盘路径（含用户名）。

- 要**发给外部**的成品 → 清理作者与公司字段
- 仅内部留档 → 可放宽

---

## 5. 归档时的强制检查

见 `docs/ARCHIVE.md` 第 2 步。本文件定义**什么算敏感**，ARCHIVE 定义**怎么查**。

---

## 6. 已入库后的补救

发现敏感信息已经推送：

1. **不要只做一次新 commit 删除文件**——文件仍在历史里
2. 立即作废该凭据 / 通知数据负责人（这一步比清理 git 更紧急）
3. 简单场景：删除文件 + `git commit` + 推送，评估历史是否可留
4. 需要彻底清除历史：使用 `git filter-repo`，**这会改写全部 commit hash，推送后需团队重新 clone**，执行前必须告知用户

> 判断标准：如果是**密钥**，作废它；如果是**个人信息**，评估暴露范围。清理 git 历史是善后，不是止损。
